## 2. Documentation material that feeds the overhaul

| Source | What it gives | Used for |
|---|---|---|
| `website/_content/groundhog/api.json` | Per function: signature, validation min/max, summary, formulas, references, examples | Tool cards, metadata auto-fill (F2), validity ranges, explainer, citations |
| 20 Groundhog tutorials (PCPT processing, SPT processing, soil profile, settlement, shallow capacity, API RP2GEO piles, De Beer, Koppejan, parameter selection, AGS loading) | Canonical call sequences of the stateful classes | Recipe tools (F4) and end-to-end gold test cases with expected numbers |
| `core/function_manifest.json` (212 functions) and `parameter_inventory.json` | Signatures and parameter units | Schema generation (existing) |
| `eval` dataset (~2,450 generated examples) | Registry-generated cases | Regression; must be extended with natural-language cases (see Phase 1) |
| Web research (below) | Constrained decoding, hybrid tool retrieval, small-model reliability | Design choices |

Web findings used (treat as secondary evidence, verify on our own benchmark per AGENTS.md §31):
- Grammar-constrained generation (llama.cpp GBNF) makes syntactically invalid tool calls impossible, which removes the malformed-call class of failure for small models ([DEV Community](https://dev.to/janpauldahlke/how-i-use-gbnf-grammars-to-make-small-local-models-stop-hallucinating-json-46g), [llama.cpp grammars](https://www.mintlify.com/ggml-org/llama.cpp/advanced/grammars)). It fixes syntax, not wrong values.
- Sub-7B models without explicit tool-calling training emit malformed calls more often, and quantisation below Q4_K_M hurts ([promptquorum](https://www.promptquorum.com/pt/power-local-llm/best-local-models-tool-calling-2026)). This matches F5, so reduce what the model must decide rather than only swapping models.
- Hybrid lexical + dense retrieval beats either alone for tool selection, and top-15 retrieval stays above 98 % accuracy at thousands of tools in published work ([arXiv 2607.15593](https://arxiv.org/pdf/2607.15593), [Re-Invoke](https://www.research.google/blog/re-invoke-tool-invocation-rewriting-for-zero-shot-tool-retrieval/)). We have ~200 tools, so a small embedding model is optional, not required.

## 3. Design principles for the overhaul

1. **Shrink the model's job.** Each model call has one narrow decision: pick a *family*, then pick a *tool* among at most 5, then fill *only the arguments not already resolvable*. Everything resolvable deterministically (units, project values, defaults from Groundhog bounds) is resolved outside the model.
2. **Constrain, then verify.** GBNF/JSON-schema constrained decoding for tool name and argument keys; the existing validator, `argument_grounding` and units layer stay as the second line.
3. **One source of truth for engineering maths:** Groundhog. GeoAI-owned maths (`cpt.py`, `spt.py`) is replaced by calls into Groundhog, with a parity test that proves the numbers did not change before the swap.
4. **Documentation-derived metadata, human-reviewed.** Method, formula, validity range, references generated from `api.json`, committed as reviewable data, not hand-typed in 197 places.
5. **Benchmark gates, not opinions.** No phase is "done" until its metrics are met on the full test split, identical seeds and tools for every model.
6. Incremental: heuristic provider stays as fallback (§27). No new heavy dependencies (§24); embeddings only if Phase 2 measurements demand it.

## 4. Target architecture

```text
User message
   |
   v
Context resolver (project, active form, CPT/borehole ids)           deterministic
   |
   v
Stage A  Router: family + candidate tools                           lexical BM25 (+ optional small embeddings), top-15
   |
   v
Stage B  Model call 1: choose tool among top-5 (grammar-constrained name)   ~800-token prompt, compact cards
   |
   v
Stage C  Argument plan: schema-pruned to *missing* args only,
         project/defaults pre-filled, grammar-constrained JSON       model call 2 (skipped when nothing is missing)
   |
   v
Validate (pydantic bounds, units.py, argument_grounding)  -- clarification question on any gap
   |
   v
Registry -> Groundhog (single functions OR recipe tools over PCPTProcessing / SPTProcessing / SoilProfile)
   |
   v
Structured result + provenance (method, formula, validity range, references from api.json)
   |
   v
Explainer: deterministic "formula & derivation" + short model narration (guarded by response_guard)
```

Why two small calls instead of one large one: prompt processing dominates CPU latency (F5/F7). A 800-token call-1 prompt with a cached system prefix replaces one ~3k-token prompt, and call 2 is skipped for fully-resolved requests.

## 5. Phases

Each phase lists work, files, and an exit gate. Phases 1-3 are independent of choosing a model.

### Phase 0: Baseline and hygiene (1-2 days)
- **Done:** manifest regenerated (matches HEAD), full-suite baseline recorded (866 pass / 1 pre-existing fail). Remaining: resolve the 235-vs-236 count; commit nothing (user commits manually).
- Decide the fate of the in-flight `multi_agent.py`: keep behind `GEOAI_MULTI_AGENT`, **default off** until Phase 4 gates pass (no extra model risk while the single path is at 45-60 %).
- Fix docs drift (F10) and add a Groundhog-version pin check to `check_keys`/manifest tests.
- Gate: tests green, no behaviour change.

### Phase 1: Evaluation foundation (3-4 days)  *do this first, everything is measured against it*
- Grow the held-out set from 40 to the **full test split** for every run (266 examples), plus a **hand-written natural-language gold set (>= 150)** written by the user's engineering knowledge, not generated from tool schemas, covering: misspelt method names, mixed units, "use the current project", CPT-id references, conflicting CPT vs borehole.
- Tutorial-derived **numeric gold cases**: run each Groundhog tutorial calculation once, store expected outputs (tolerance 1 %), and use them as end-to-end oracles for recipe tools.
- Split metrics: *router recall@5/@15*, *tool accuracy given correct candidates*, *argument accuracy*, *clarification precision/recall*, latency, tokens.
- Gate: reproducible `python -m core.geoai.eval.runner` numbers on full splits for heuristic and Qwen3-1.7B/4B, committed as the new baseline.

### Phase 2: Tool retrieval and routing (4-5 days)
- Measure router recall@5/@15 on the gold set (current lexical recall was 0.595 on generated data).
- Add family-level routing (category -> tool) and cards enriched from `api.json` summaries and parameter names.
- Only if lexical recall@15 < 0.95: evaluate a small embedding model (e.g. a ~25-100 MB sentence encoder via the existing llama.cpp runtime, cached to SQLite), fused by reciprocal rank. Otherwise keep pure BM25 (§13, §24).
- Gate: recall@15 >= 0.95 and recall@5 >= 0.85 on the gold set.

### Phase 3: Groundhog-first consolidation (1-2 weeks)
- **3a Parity tests**: for CPT (`cpt.py`) and SPT (`spt.py`) compare current outputs with Groundhog `pcpt_correlations` / `spt_correlations` over a grid of inputs, document every difference.
- **3b Replace** in-house formulas by Groundhog calls where equal within tolerance; where Groundhog is different or missing, keep the GeoAI code but label it explicitly as a GeoAI-implemented method in provenance (and prefer an upstream issue over a permanent fork, as already done for the two stress corrections in `tool_definitions.py`).
- **3c Recipe tools** (F4): thin, deterministic multi-step tools built from the tutorial sequences, each with explicit schema and provenance:
  1. `process_project_cpt` (load -> normalise -> layering -> correlations)
  2. `process_project_spt`
  3. `derive_design_profile` (parameter selection, `Eurocode7` characteristic value)
  4. `calculate_settlement_profile` (existing, extend to layered)
  5. `calculate_pile_capacity` family: API RP2GEO, LCPC, Koppejan, De Beer, selectable by `method`
  Stateful Groundhog objects stay hidden; recipes are the only door (§7).
- **3d Metadata generation**: script `tools/build_tool_metadata.py` reads `api.json` and writes `tool_metadata_generated.json` (method, formula, references, validity min/max, units); curated `TOOL_METADATA` overrides it. Target 197/197 coverage; reviewable diff.
- Gate: parity report with no unexplained diffs; recipes pass tutorial gold numbers; metadata coverage 100 %.

### Phase 4: Reliable small-model orchestration (1-2 weeks)
- Provider: add grammar/JSON-schema constrained decoding for the tool-name and argument stages (llama-cpp-python `grammar` / `response_format`), behind a config flag, falling back to the current path.
- Implement the Stage B/C split from section 4 with a cached system-prompt prefix (KV reuse already partly present).
- Argument pre-fill and pruning: project values, defaults from schema bounds, unit-aware extraction from the user text *by regex + `units.py`* before the model is asked; model only fills what remains; `argument_grounding` still blocks invented numbers.
- Clarification policy made explicit and rule-checked (missing required arg -> question, never a default), targeting the 0-50 % missing_data category.
- Gate (CPU, Qwen3-1.7B class, full test split + gold): strict pass >= 75 %, hallucinated-parameter rate <= 5 %, clarification accuracy >= 85 %, p50 end-to-end <= 15 s on the reference CPU. If not reachable, record that and move to Phase 5 with a GPU-optional recommendation instead of shipping a 60 s assistant.

### Phase 5: Model selection and fine-tuning (as in plan.md Stage 10-11, now on the new pipeline)
- Benchmark Qwen3 (1.7B/4B), Gemma 3, Phi-4-mini, Granite, SmolLM3 with the Phase 4 pipeline (constrained vs not), identical tools and prompts.
- Failure collection from `geoai_turns.jsonl` and eval into SFT/GRPO data **only for decisions that remain model-bound** (tool choice among 5, argument extraction, clarification). Keep the adapter only if it beats base per the existing go/no-go rules.
- Gate: decision record (model, quant, `n_ctx`, `max_tools`, latency/RAM budget).

### Phase 6: Research, evidence and explanation (1-2 weeks)
- Index the bundled Groundhog docs (formulas, validity ranges, references) into the local FTS5 index as `[Standards / Guidance]`/`[Literature]` evidence with source pointers; the explainer cites the exact reference listed in Groundhog's docstring, never a model-generated citation (§11).
- Evidence panel in `GeoAICopilot.jsx`: tool, inputs with units, method, assumptions, sources, evidence tier. Optional web research stays opt-in.
- Gate: citation-accuracy tests (every shown reference exists in the index); UI test for the panel.

### Phase 7: Packaging and release
- Installer size and cold-start check, first-run model download flow, idle unload, eval-subset CI, version bump per `RELEASE_GUIDE.md`.

## 6. Risks and open questions

| Risk | Mitigation |
|---|---|
| Phase 4 latency target may be unreachable on low-end CPUs | Measure early on `estimate_desktop_latency.py`; offer an opt-in GPU/larger-model profile; keep the deterministic fast paths (project lookups, formulas explainer) model-free |
| Replacing `cpt.py` formulas changes numbers users have seen | Parity report first; version note in the changelog; provenance shows method |
| Groundhog bugs (two already worked around) | Keep upstream-correction pattern with tests; track in a `KNOWN_UPSTREAM_ISSUES` table |
| Constrained decoding raises latency or degrades reasoning | Measure with and without; apply only to tool-name/args stages |
| Dense retrieval adds dependency weight | Gate on measured recall (Phase 2) |

Decisions taken (user delegated: "plan yourself, I want the best"; revisit any of these on request):
1. **Hardware budget:** reference machine = 8-core CPU laptop, 16 GB RAM, no GPU. Target p50 end-to-end <= 15 s; optional GPU profile is an add-on, never required.
2. **Gold set:** I draft the ~150 natural-language requests (with expected tool/arguments verified by running Groundhog), the user reviews and edits; items are tagged `reviewed: false` until then and excluded from gating numbers.
3. **Multi-agent:** keep the code, **default off** until Phase 4 gates pass.
4. **Priority:** reliability first (Phases 1, 2, 4) with Phase 3a/3d (parity and metadata, no behaviour change) in parallel; recipe tools (3c) after the Phase 2 router gate.
